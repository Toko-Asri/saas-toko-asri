# Toko Asri Tahap 2 (ERP) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Modul ERP: kasir/POS dengan pengurangan stok FEFO yang atomik, riwayat dan struk, penyesuaian stok (rusak/kedaluwarsa/hilang/koreksi), dan laporan keuangan sederhana (penjualan, HPP, laba kotor, kerugian stok) untuk pemilik.

**Architecture:** Sama seperti Tahap 1: logika kritis di Postgres (RPC `checkout`, `adjust_stock`, `laporan_*`) dan trigger saran pembelian Tahap 1 otomatis aktif karena `checkout` menurunkan `batches.qty`. Next.js hanya antarmuka; keranjang POS adalah satu komponen klien, aturan hitung dipisah di `src/lib/pos-cart.ts` agar teruji unit. Perubahan skema HANYA lewat file migration baru (Tahap 1 sudah dijalankan pengguna di Supabase demo).

**Tech Stack:** Next.js 16 (App Router, `proxy.ts`), TypeScript, Tailwind, `@supabase/ssr`, Vitest, Postgres 16 lokal untuk uji SQL.

**Spec:** `docs/superpowers/specs/2026-11-19-toko-asri-design.md` (Tahap 2); lanjutan dari `docs/superpowers/plans/2026-11-19-tahap1-scm.md`.

## Global Constraints

- UI Bahasa Indonesia; Rupiah lewat `formatRupiah` (`src/lib/format.ts`); "hari ini" selalu tanggal **Asia/Jakarta** (`hariIniJakarta()` di TS, `(now() at time zone 'Asia/Jakarta')::date` di SQL).
- Batch **kedaluwarsa** = `tgl_kedaluwarsa <= hari ini (WIB)`; tidak boleh terjual (konsisten dengan `expiryStatus`).
- Perubahan skema/fungsi hanya file baru di `supabase/migrations/` (nama `2026112x...`, berurutan); jangan mengedit migration Tahap 1. Tidak dijalankan ke Supabase pengguna; uji hanya di Postgres lokal via `supabase/tests/run.sh`.
- Peran: `pemilik` semua; `kasir` kasir + riwayat penjualan miliknya + baca stok; `staf_gudang` gudang + penyesuaian stok, **tanpa** akses penjualan/laporan. Semua tabel baru ber-RLS; tulis hanya lewat RPC (insert/update/delete di-revoke dari `authenticated`).
- Harga jual dan HPP dibaca server saat `checkout` (tidak pernah dipercaya dari klien).
- Fungsi `security definer` memakai `set search_path = public, pg_temp`.
- Setiap tugas: tes gagal dulu, lalu implementasi; akhir tugas `npm test` + `npm run build` (dan `run.sh` untuk tugas SQL) lulus; commit berakhiran trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` dan `Claude-Session: https://claude.ai/code/session_01NjswzVeNpJvCu4pynPEeRZ`.
- Branch kerja: `claude/vigilant-noether-ivli6h` (sesuai aturan sesi); PR ke `main` di akhir tahap; push/PR hanya sesuai permintaan pengguna.

## Review Focus

- Menjual **tepat unit terakhir** berhasil; menjual lebih dari stok layak jual ditolak **tanpa mengubah stok sebagian** (atomik) — Task 2.
- Batch yang kedaluwarsa **hari ini** tidak ikut terjual walau paling awal; permintaan yang hanya bisa dipenuhi batch kedaluwarsa ditolak — Task 2.
- **Dua kasir** menjual unit terakhir bersamaan: satu berhasil, satu ditolak, stok tidak negatif — Task 2 (skrip konkurensi).
- **Klik ganda/kirim ulang** (kunci idempotensi sama) tidak membuat dua transaksi dan tidak mengurangi stok dua kali — Task 2.
- Bayar kurang dari total, keranjang kosong, qty ≤ 0 atau pecahan, produk nonaktif ditolak — Task 2 dan Task 5.
- Harga produk berubah antara keranjang dibuka dan checkout: struk memakai harga **saat checkout**, tersimpan sebagai snapshot — Task 2.
- Penyesuaian yang membuat stok batch negatif ditolak; kenaikan stok hanya untuk alasan `koreksi` — Task 3.
- Kasir tidak bisa membuka `/laporan` atau `/gudang/*` dan hanya melihat penjualannya sendiri — Task 1 dan Task 5.

### Task 2: RPC `checkout` (FEFO, atomik, idempoten)

**Files:** Create `supabase/migrations/20261120000300_erp_checkout.sql`, `supabase/tests/erp_concurrency.sh`; Modify `supabase/tests/erp_test.sql`.

**Interfaces:**
- Produces: `checkout(p_items jsonb, p_metode text, p_bayar numeric, p_key uuid) returns uuid` dengan `p_items = [{product_id, qty}]`; izin `pemilik`/`kasir`, selain itu error `Tidak diizinkan`. Perilaku: kunci sama → kembalikan `sales.id` yang ada tanpa efek baru; gabungkan baris produk yang sama; urutkan produk menurut `product_id` sebelum mengunci (hindari deadlock); per produk ambil batch **layak jual** (`tgl_kedaluwarsa > hari ini WIB`, `qty > 0`) urut `tgl_kedaluwarsa, id` dengan `for update`, kurangi hingga terpenuhi, satu `sale_items` per batch yang dipakai (`harga_jual` = `products.harga_jual` saat itu, `hpp_satuan` = `coalesce(batches.harga_beli, products.harga_beli)`); `total` = Σ qty×harga_jual; tolak bila produk tak ada/nonaktif, qty bukan bilangan bulat > 0, stok layak kurang (pesan menyebut nama produk dan sisa), keranjang kosong, `p_bayar < total` (untuk `qris`/`transfer` `bayar` harus = total), metode tidak valid; `kembalian = p_bayar - total`.
- Consumes: `batches`, `products`, trigger `batches_saran` (Tahap 1; otomatis memicu saran bila stok ≤ minimum).
